🧱 Día 115 — Aprendizaje clave: Datos Hardcodeados, el "DNI Falso" en Angular y la Flexibilidad Arquitectónica

🧠 Qué entendí hoy (explicado simple)
Entendí que el navegador es muy obediente pero completamente ciego. Si yo inicio sesión con un usuario nuevo, pero en el código dejé escrito "siempre envía el número 1", el navegador le hará caso al código. El servidor recibe ese número 1, revisa sus registros, ve que el usuario 1 ya hizo la tarea y bloquea todo gritando "¡Fraude!". Descubrí que los sistemas de seguridad son implacables, y si les envío datos "quemados" (hardcodeados), el sistema colapsa haciendo exactamente aquello para lo que lo programé.

⚙️ Cómo funciona (paso a paso real)

Detección en Red: Usé la pestaña Network (F12) y descubrí que Angular estaba enviando un JSON con usuarioId: 1 a pesar de haberme logueado con alumno_beta@tesis.com.

El Bloqueo: El EvaluacionService en Spring Boot recibió el ID 1, comprobó en PostgreSQL que el Arquitecto ya había completado la lección, y lanzó un error 409 Conflict (Fraude Detectado).

La Relajación Temporal (Bypass): Para no arruinar la auditoría visual con el usuario real de hoy, fui a IntelliJ, comenté temporalmente el throw new LeccionYaCompletadaException(...) en el servicio y desplegué de nuevo en Azure.

La Prueba Empírica: Permití que el usuario beta usara el sistema fluyendo libremente para anotar la fricción visual, sabiendo que mañana me toca programar la extracción dinámica del ID desde el JWT.

🧱 Regla de oro del día
👉 "El código del frontend hace exactamente lo que le escribes, no lo que tú asumes. Hardcodear datos rompe la telemetría."

❌ Qué pensaba antes
Pensaba que por el simple hecho de iniciar sesión con un correo diferente en la pantalla de Login, toda la aplicación de Angular automáticamente "sabría" que debía usar el ID de ese nuevo usuario para todas las peticiones posteriores.

✅ Qué entiendo ahora
Entiendo que Angular no tiene "conciencia" del usuario a menos que yo lo programe explícitamente. Cada petición HTTP es independiente. Si no extraigo dinámicamente el usuarioId del Token JWT y lo inyecto en el DTO, Angular seguirá enviando ciegamente la variable estática que yo dejé olvidada en el código (usuarioId: 1).

🔥 Diferencia clave

Antes: Asumía que un error 409 significaba un fallo grave en la base de datos o en la red, e intentaba borrar todo sin mirar el contenido del mensaje.

Ahora: Leo el Payload en la pestaña Network de Chrome, detecto que el dato enviado está mal (ID 1), entiendo que mi regla antifraude está funcionando a la perfección, y aplico un parche táctico en el backend para poder continuar con mi trabajo de campo.

🎯 Ejemplo que puedo explicar
Es como prestarle tu chaqueta a un amigo para que entre a un club. El amigo tiene su propio rostro (inició sesión correctamente), pero en el bolsillo de la chaqueta olvidaste tu DNI (el usuarioId: 1 hardcodeado). Cuando el guardia de seguridad (Spring Boot) revisa el DNI, ve que tú ya estás adentro del club, así que no deja pasar a tu amigo y grita "¡Intento de fraude!" (Error 409). La culpa no es del guardia, es tuya por dejar el DNI equivocado en el bolsillo.

🧠 Dónde vive cada cosa (ARQUITECTURA)

Lógica (quién decide): EvaluacionService en Spring Boot (el guardia estricto que detecta el fraude y lanza el 409).

Ejecución (quién hace): leccion.component.ts en Angular (el amigo que entrega ciegamente el DNI equivocado porque así se lo programó).

Persistencia (quién guarda): Azure Database for PostgreSQL (la bóveda que recuerda que el usuario 1 ya había pasado por ahí).

Transporte (quién solo pasa datos): La pestaña Network (DevTools) interceptando el JSON rebelde.

# Lección de arquitectura: contrato de errores Backend → Frontend

> **Principio aplicado:**
> **Observo. Comprendo. Corrijo. Avanzo.**

## Contexto

Durante las pruebas de la lección 7 se detectó un comportamiento aparentemente extraño:

* Opción A → `200 OK`, respuesta incorrecta.
* Opción C → `409 Conflict`.
* Opción B → `200 OK`, respuesta correcta.

La primera impresión fue pensar que el Backend estaba rechazando incorrectamente la opción C.

Después de revisar las peticiones realizadas desde Angular y el comportamiento del Backend, se identificó que el problema estaba relacionado con **múltiples peticiones consecutivas** provocadas por un doble clic.

---

## Diagnóstico

En la pestaña **Network** se observaron varias peticiones `decidir` realizadas prácticamente al mismo tiempo.

El Backend detectó la concurrencia y aplicó su mecanismo de protección de idempotencia, devolviendo:

```text
Estamos procesando tu solicitud. Por favor, no hagas doble clic.
```

Por lo tanto:

**Spring Boot estaba funcionando correctamente.**

El problema estaba en la interpretación que hacía Angular del código HTTP `409`.

---

## El problema arquitectónico

El Frontend tenía una regla estática:

```typescript
if (err.status === 409) {
  this.esCorrecto = false;
  this.tituloFeedback = 'Aviso del Sistema';
  this.mensajeFeedback =
    'Ya has completado esta lección anteriormente. ¡Avanza al siguiente desafío!';
  this.mostrarFeedBack = true;
}
```

Aquí aparece el problema:

Angular interpretaba:

```text
409 = Lección completada anteriormente
```

Pero el Backend podía utilizar `409 Conflict` para diferentes situaciones de conflicto.

Por ejemplo:

```text
409 → Lección ya completada
409 → Solicitud duplicada / doble clic
409 → Otro conflicto de negocio
```

El Frontend estaba tomando una decisión basándose únicamente en el código HTTP e ignorando el mensaje específico enviado por el Backend.

---

## Corrección

El Backend ya enviaba información útil dentro de la respuesta JSON.

Por lo tanto, Angular debe utilizar esa información:

```typescript
error: (err) => {

  if (err.status === 409) {
    this.esCorrecto = false;
    this.tituloFeedback = 'Aviso del Sistema';

    this.mensajeFeedback =
      err.error?.mensaje ||
      'Ya has completado esta lección o ocurrió un conflicto.';

    this.mostrarFeedBack = true;

  } else {

    this.esCorrecto = false;
    this.tituloFeedback = 'Error de conexión';

    this.mensajeFeedback =
      'Ocurrió un problema de conexión con el Motor de Decisiones.';

    this.mostrarFeedBack = true;
  }
},
```

### Resultado

Ahora el flujo queda:

```text
Spring Boot
     │
     │  HTTP 409
     │
     │  {
     │    "mensaje": "Estamos procesando tu solicitud..."
     │  }
     ▼
  Angular
     │
     │ lee err.error.mensaje
     ▼
  Usuario
     │
     ▼
Mensaje real del Backend
```

---

# Decisión arquitectónica

### ¿Quién es el dueño de la lógica?

**Backend / Spring Boot**

El Backend es dueño de las reglas de negocio y determina por qué una operación fue rechazada.

### ¿Quién solo delega?

**Angular**

Angular recibe la respuesta y decide cómo presentarla visualmente al usuario.

### ¿Quién transporta los datos?

**HTTP + JSON**

El protocolo HTTP transporta el código `409` y el cuerpo de la respuesta.

---

# Regla de oro

> **El Backend decide qué ocurrió.
> El Frontend decide cómo mostrarlo.
> HTTP transporta la información entre ambos.**

Esto evita que Angular tenga que adivinar el significado de una respuesta.

---

# Lección aprendida

Un código HTTP como `409` representa una categoría de situación: **conflicto**.

El significado concreto del conflicto pertenece al contrato de comunicación entre Backend y Frontend.

Por eso, ante un error:

```text
Código HTTP
     +
Datos de respuesta
     ↓
Interpretación
     ↓
Presentación al usuario
```

La interfaz debe aprovechar la información que el Backend ya proporciona.
