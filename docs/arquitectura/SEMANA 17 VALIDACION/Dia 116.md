# 🧪 Preparación del entorno de telemetría forense

## 🎯 Objetivo

Preparar las herramientas de telemetría y monitoreo antes de iniciar las pruebas con el **Usuario 2**.

El objetivo es garantizar que todos los eventos relevantes del sistema queden registrados durante la ejecución de la prueba. No es posible realizar una auditoría adecuada del comportamiento del sistema bajo estrés si previamente no se cuenta con mecanismos de observación y registro.

---

## 🗄️ 1. La Bóveda — Limpieza del entorno

Abrir **DBeaver** o **pgAdmin** y conectarse a la instancia de **Azure Database for PostgreSQL**.

Antes de iniciar la prueba, limpiar los registros de progreso generados durante las ejecuciones anteriores.

Ejecutar:

    DELETE FROM progresos;

Esto permite iniciar la prueba desde un estado limpio y controlado, evitando que los datos de pruebas anteriores interfieran con los resultados obtenidos.

---

## 📡 2. El Radar — Monitorización en tiempo real

Ingresar al **Portal de Azure**:

https://portal.azure.com

Acceder al **App Service** donde se encuentra desplegada la aplicación **Spring Boot**.

Desde el menú lateral, ingresar a:

> **Log stream (Flujo de registros)**

Mantener el **Log Stream** abierto durante toda la ejecución de la prueba.

Esta herramienta permitirá observar en tiempo real los eventos generados por el backend, especialmente:

- `Exception`
- `StackTrace`
- Errores de ejecución.
- Fallos relacionados con las peticiones HTTP.
- Errores producidos durante el procesamiento de las respuestas.
- Comportamiento inesperado de la aplicación.

De esta manera, cualquier error producido durante la prueba podrá ser identificado y analizado posteriormente.

---

## 👤 3. El Perfil — Preparación del Usuario 2

Para garantizar que la prueba se ejecute con una identidad nueva, se debe crear un nuevo usuario en la base de datos o permitir que el **Usuario 2** complete el proceso de registro desde cero.

El objetivo es disponer de una sesión nueva y generar un **token JWT fresco**, evitando utilizar información asociada a sesiones anteriores.

> **Nota:** Para esta prueba se creó un nuevo usuario directamente desde la base de datos.

# 🔐 Corrección de la identidad del usuario mediante JWT

## 📝 Commit

`fix(frontend): extraer dinámicamente la identidad del usuario desde el token JWT`

---

## 📌 Descripción del cambio

Se realizó una modificación en el frontend para eliminar el uso de un identificador de usuario fijo y obtener dinámicamente la identidad del usuario autenticado a partir del **token JWT**.

Anteriormente, el `usuarioId` se encontraba definido de forma estática en `leccion.component.ts`, lo que podía provocar que diferentes usuarios fueran procesados utilizando el mismo identificador.

Con esta modificación, la aplicación obtiene la identidad directamente desde el token correspondiente a la sesión autenticada.

---

## 🔄 Cambios realizados

- Se elimina el `usuarioId` **hardcodeado** en `leccion.component.ts`.
- Se implementa la decodificación del **payload del JWT**.
- Se utiliza `atob()` para realizar la decodificación en **Base64**.
- Se obtiene dinámicamente el identificador del usuario autenticado.
- Se actualiza `RespuestaEstudianteDTO` para enviar la identidad correspondiente al usuario actual.
- El **Motor de Decisiones** recibe ahora la información asociada al usuario autenticado.
- Se evita depender de un identificador de usuario fijo durante la ejecución de las pruebas.

---

## 🔄 Flujo de autenticación implementado

    Usuario 2
        ↓
    Inicio de sesión
        ↓
    Generación del Token JWT
        ↓
    Obtención del Payload
        ↓
    Decodificación mediante Base64
        ↓
    Extracción del usuarioId
        ↓
    RespuestaEstudianteDTO
        ↓
    Motor de Decisiones
        ↓
    Procesamiento de la respuesta

---

## 🎯 Resultado

La aplicación deja de utilizar una identidad estática y pasa a trabajar con la **identidad real del usuario autenticado mediante su token JWT**.

Esto permite que cada sesión sea procesada utilizando el `usuarioId` correspondiente y evita inconsistencias ocasionadas por el uso de identificadores fijos.

Además, esta modificación permite realizar pruebas con diferentes usuarios sin necesidad de modificar manualmente el código del frontend.

Decodificación Dinámica del JWT (Seguridad Stateless): Eliminaste la deuda técnica del usuarioId quemado en tu código de Angular. Aplicando el principio de que el JWT es un pasaporte criptográfico cuyas primeras dos partes (Header y Payload) viajan en formato Base64 de lectura pública, implementaste la función atob() para extraer la identidad real del usuario sin depender de sesiones en la memoria del servidor.

Blindaje Físico contra Concurrencia (DBA en la Nube): Sometiste al sistema a un "ataque de ansiedad" con clics frenéticos y descubriste que la latencia de la red superaba la validación en memoria de Java. Para garantizar una persistencia inmutable de los datos, forjaste un candado físico (UNIQUE CONSTRAINT) directamente en Azure Database for PostgreSQL, reafirmando que tu objetivo principal es la claridad del diseño y la toma de decisiones por encima de la simple velocidad de codificación.

Gestión Inteligente de Excepciones (El Frontend Ciego): Reparaste la amnesia de la interfaz ante los errores HTTP 409. Fiel a tu diseño donde el frontend es un "cliente ciego" y el backend es el juez absoluto de la seguridad, configuraste a Angular para que lea dinámicamente el JSON estructurado que emite tu @ControllerAdvice, evitando que la aplicación colapse y mostrando mensajes amigables al usuario.

Auditoría de Resiliencia (El Salto Cuántico): Ejecutaste pruebas de manipulación de URLs en el navegador para intentar acceder a lecciones bloqueadas. Esto te permitió observar la reacción de la infraestructura y sentar las bases para tu próxima iteración de guardianes de rutas (Guards), garantizando que aunque la vista ceda, tu filtro en Spring Boot detendrá cualquier intrusión.

Identificación de Deuda Arquitectónica: Diagnósticaste el "callejón sin salida" visual que ocurre al iniciar sesión nuevamente. Al comprender que las arquitecturas modernas son Stateless y el servidor tiene "amnesia" por diseño, identificaste la necesidad futura de un endpoint de reanudación para sincronizar la interfaz visual sin acoplar el servidor.
